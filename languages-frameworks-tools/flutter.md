# Flutter手册

量潮工作手册语言、框架和工具目录下的 Flutter 子手册，讲的是怎么把一个跨平台应用从界面原型推进到可构建、可测试、可发布的交付物。Flutter 手册的重点不是“怎么写 widget”，而是目标平台、工程结构、资源、状态、插件、测试和发布证据要一起闭环。

## 跨平台场景

- 移动端、Web、桌面端或多端复用的 Flutter 应用。
- 单一代码库覆盖多个平台，但需要区分平台能力和发布条件的项目。
- 需要统一管理 UI、状态、路由、资源、主题和构建流程的应用。
- 需要接入 Dart package、原生 plugin、签名证书和应用商店发布的场景。

## 应用工程原则

- 先确定目标平台和最低支持版本，再定工程结构。
- `pubspec.yaml` 是工程入口，依赖、资源、字体和元数据都要保持干净。
- 先确定 widget、状态、路由和主题边界，再做页面细节。
- 平台差异要显式处理，不能靠“某个平台刚好能跑”。
- 测试、构建、签名和发布证据要在发布前闭环。
- 插件和原生能力接入要提前确认权限、兼容性和回退方案。

## 应用交付角色

- 负责人确认目标平台、功能范围、验收口径和发布顺序。
- 开发负责页面、组件、状态、路由、主题和插件接入。
- 测试负责功能、布局、兼容性、设备差异和回归验证。
- 平台负责 SDK、签名、证书、构建产物和发布账号。
- AI 负责整理结构、生成样例、提示遗漏和辅助排查构建错误。

## Flutter 工程对象

| 对象 | 含义 |
|------|------|
| `project` | Flutter 项目本体 |
| `pubspec.yaml` | 依赖、资源和元数据定义 |
| `widget tree` | 页面与组件的层级结构 |
| `package` | 可复用 Dart 包 |
| `plugin` | 对接原生能力的插件 |
| `asset` | 图片、字体和其他资源 |
| `build mode` | debug、profile、release 等构建模式 |
| `test` | 单元、组件和集成测试 |

## 从环境到上架

### SDK 和工具链

先把 Flutter 开发环境准备好。环境不稳定时，后续页面问题和构建问题会混在一起。

- 安装 Flutter SDK
- 跑 `flutter doctor`
- 选定编辑器或 IDE
- 确认目标平台所需工具链

### 工程结构

把工程结构先定清楚。Flutter 项目要让页面、组件、状态、资源和测试各在合适的位置。

- `pubspec.yaml` 放在项目根目录
- `lib/` 放入口和业务代码
- `assets/` 放图片、字体和静态资源
- `test/` 放单元测试和组件测试
- `integration_test/` 放集成测试
- `android/`、`ios/`、`web/`、`macos/`、`windows/`、`linux/` 按目标平台使用

### 页面和状态开发

开发阶段把 UI 和逻辑做成可追踪的改动。重点关注状态边界、平台差异和资源引用。

- 明确入口页面
- 控制 widget 层级
- 管理状态、路由和主题
- 处理不同屏幕尺寸和平台差异
- 记录插件接入和原生交互

### 多端测试

测试阶段确认应用不只是能打开。移动端、Web 和桌面端的布局、输入、权限和导航都要分别看。

- 跑 `flutter test`
- 写 widget test 和必要的 unit test
- 写 integration test 验证关键流程
- 检查不同设备、分辨率和平台上的表现

### 构建、签名和发布

发布前先把目标产物、签名要求和发布渠道说清楚。不同平台的发布条件不能混在一起。

- 选择对应平台的构建命令
- 确认 release 模式
- 确认签名、证书和发布账号
- 检查产物是否可安装或可访问
- 保留构建和发布证据

### 版本和兼容性维护

维护阶段处理后续变化和兼容性。Flutter SDK、插件和原生平台升级都可能引入 breaking change。

- 升级 Flutter SDK
- 升级依赖包
- 记录 breaking change
- 清理不再使用的插件和资源
- 保持文档和代码同步

## 应用类型

- 移动端业务应用：重点看权限、离线状态、安装包和应用商店要求。
- Web 控制台：重点看路由、响应式布局、加载速度和浏览器兼容。
- 桌面工具：重点看窗口尺寸、文件权限、系统菜单和安装方式。
- 跨平台原型：重点看复用边界和后续是否会变成正式产品。
- 内部演示应用：重点看展示路径、数据隔离和临时功能清理。

## 应用交付标准

- 支持平台、最低版本和发布渠道清楚。
- 启动入口、路由结构和主要页面清楚。
- `pubspec.yaml`、资源、字体、依赖和插件说明清楚。
- 单元、组件或集成测试覆盖关键流程。
- 构建、签名和发布流程可复现。
- 兼容性风险、回退方式和发布证据清楚。

## 发布前检查

- `flutter doctor` 是否通过
- `pubspec.yaml` 是否整理好
- 入口文件和页面结构是否清楚
- 是否有 widget 和集成测试
- 是否明确 build target 和签名
- 是否记录插件兼容性
