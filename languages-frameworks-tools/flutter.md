# Flutter手册

量潮工作手册语言、框架和工具目录下的 Flutter 子手册，讲的是怎么把 Flutter 用在跨平台应用、界面交付、插件接入、测试和发布里，并把开发、构建、验收和维护连成一条可执行的线。

## 适用范围

- 适用于移动端、Web 和桌面端应用。
- 适用于单一代码库覆盖多个平台的项目。
- 适用于需要把 UI、状态、资源和发布流程一起管理的项目。
- 适用于需要把 Flutter 和 Dart package 或 plugin 协同使用的场景。

## 工作原则

- 先定支持平台，再定工程结构。
- 先定 `pubspec.yaml`，再定依赖和资源。
- 先定 widget 和状态边界，再做页面和交互。
- 代码、资源、配置和文档要同步。
- 测试和构建要在发布前闭环。
- 插件和原生能力接入要提前确认兼容性。

## 角色分工

- 负责人负责确认目标平台、范围和验收口径。
- 开发负责实现页面、状态、路由和插件接入。
- 测试负责验证功能、布局、兼容性和回归。
- 平台负责环境、签名、构建和发布流程。
- AI 负责整理结构、生成草稿和提示遗漏。

## 关键对象

| 对象 | 含义 |
|------|------|
| `project` | Flutter 项目本体 |
| `pubspec.yaml` | 依赖、资源和元数据定义 |
| `widget tree` | 页面与组件的层级结构 |
| `package` | 可复用 Dart 包 |
| `plugin` | 对接原生能力的插件 |
| `asset` | 图片、字体和其他资源 |
| `build mode` | debug、profile、release 等构建模式 |
| `test` | 单元、组件和集成测试 |

## 工作链路

### 环境

先把 Flutter 开发环境准备好。

- 安装 Flutter SDK
- 跑 `flutter doctor`
- 选定编辑器或 IDE
- 确认目标平台所需工具链

### 结构

把工程结构先定清楚。

- `pubspec.yaml` 放在项目根目录
- `lib/` 放入口和业务代码
- `assets/` 放图片、字体和静态资源
- `test/` 放单元测试和组件测试
- `integration_test/` 放集成测试
- `android/`、`ios/`、`web/`、`macos/`、`windows/`、`linux/` 按目标平台使用

### 开发

开发阶段把 UI 和逻辑做成可追踪的改动。

- 明确入口页面
- 控制 widget 层级
- 管理状态、路由和主题
- 处理不同屏幕尺寸和平台差异
- 记录插件接入和原生交互

### 测试

测试阶段确认应用不只是能打开。

- 跑 `flutter test`
- 写 widget test 和必要的 unit test
- 写 integration test 验证关键流程
- 检查不同设备、分辨率和平台上的表现

### 构建与发布

发布前先把目标产物和签名要求说清楚。

- 选择对应平台的构建命令
- 确认 release 模式
- 确认签名、证书和发布账号
- 检查产物是否可安装或可访问
- 保留构建和发布证据

### 维护

维护阶段处理后续变化和兼容性。

- 升级 Flutter SDK
- 升级依赖包
- 记录 breaking change
- 清理不再使用的插件和资源
- 保持文档和代码同步

## 常见场景

- 移动端业务应用
- Web 控制台
- 桌面工具
- 跨平台原型
- 内部演示应用

## 交付标准

- 支持平台清楚
- 启动入口清楚
- `pubspec.yaml`、资源和依赖说明清楚
- 测试通过
- 构建和发布流程可复现
- 兼容性和回退记录清楚

## 快速检查

- `flutter doctor` 是否通过
- `pubspec.yaml` 是否整理好
- 入口文件和页面结构是否清楚
- 是否有 widget 和集成测试
- 是否明确 build target 和签名
- 是否记录插件兼容性
