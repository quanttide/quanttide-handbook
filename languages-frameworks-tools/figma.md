# Figma手册

量潮工作手册语言、框架和工具目录下的 Figma 子手册，记录产品原型、设计语言、组件复用、响应式设计、Flutter 协作、插件、版本历史和团队评审的工作约定。Figma 在量潮不是单纯的画图工具，而是把产品想法、界面状态、交互路径和前端实现边界提前摆到同一张画布上。

这本手册的重点不是泛讲 Figma 功能，而是让产品、设计、研发能围绕同一个文件完成原型、评审、修改和交付。

当前版本只固化已经能从既有资料确认的内容：创建原型、添加 Prototype 交互、创建和复用 component、使用模板、围绕 Material Design 和 Flutter 做设计语言、按小/中/大理解断点、使用插件、用 Angular Git commit message 风格记录版本历史。没有确认过的具体断点数值、固定页面命名模板、统一组件库分组和插件清单，不写成量潮正式规范。

## 使用场景

- 产品早期把业务流程画成低保真或高保真原型。
- 研发实现前确认页面结构、组件边界、表单状态和交互路径。
- Flutter 项目把 Material Design、网格、颜色、断点和组件组合提前对齐。
- 团队评审时在同一个 Figma 文件里评论、修改和确认版本。
- 教学或新人训练时用官方模板、社区模板，或经确认后公开的量潮课堂原型快速上手。

## 文件和画布

Figma 文件先按工作对象分清层级：

| 对象 | 当前确认用途 |
|------|----------|
| Project | 项目容器，用来归集一组 Figma 文件 |
| File | 具体设计文件，可以新建、打开已有文件或导入现有设计 |
| Page | 文件下的页面分区，用来分开低保真、高保真、组件、交互流等内容 |
| Frame | 具体画布，承载页面、流程节点、组件状态或目标设备尺寸 |

正式项目暂不固定统一页面命名模板，但至少要把这些内容分开：

- 需求摘要或设计目标。
- 低保真流程。
- 高保真界面。
- 可点击原型。
- 可复用组件。
- 历史方案或归档版本。

文件和页面命名要能看出项目、模块和状态，不使用只靠个人记忆理解的名字。

## 第一个原型

新建原型时先把流程跑通，再补视觉细节。

1. 创建 Project，确认它承载哪一组设计文件。
2. 创建 File，文件名写清产品、模块和迭代。
3. 创建 Page，至少区分低保真、高保真和原型演示。
4. 添加 Frame，按目标设备或断点建立画布。
5. 添加按钮、菜单、表单、列表、弹窗等界面元素。
6. 进入 Present 预览，检查主流程能否走完。
7. 通过 Share 分享给团队，设置访问权限、有效期和评审范围。

早期原型可以粗糙，但不能只剩静态截图。进入研发实现前，要根据项目实际检查登录态、空状态、错误状态、加载状态、提交成功和提交失败等关键状态是否需要补齐。

## 交互动作

交互动作统一在 Prototype 面板里维护。常见动作包括：

- 单击按钮进入下一页。
- 悬停展示提示或状态变化。
- 拖动触发列表、卡片或流程变化。
- 跳转到指定 Frame 或页面位置。

做交互时要先覆盖主流程，再补边缘流程。一个 Figma 原型如果只能展示静态页面，研发无法确认页面之间的状态流转；如果交互太细但业务流程没走通，也会拖慢评审。

## 设计语言

量潮 Figma 文件优先围绕 Material Design 和 Flutter 协作建立设计语言。网格、颜色和 Flutter 响应式是最先要沉淀的三类规范。

### 网格

网格用于约束页面结构，不只是装饰线。

- 页面 Frame 要标出基础网格和主要内容区。
- 移动端、平板、桌面端要分别说明布局变化。
- 表格、表单、列表、卡片和导航栏要和网格对齐。
- Material Design 的 layout grid 可以作为默认参考。

### 颜色

颜色规范要能被研发复用。

- 主色、辅助色、背景色、边框色、文本色和状态色分开记录。
- 项目需要用到的状态色要分开记录，例如成功、警告、错误、禁用和信息提示。
- 不只给截图，要给颜色值和使用场景。
- 学习资料可以作为参考，但量潮项目交付时必须沉淀成自己的颜色命名。

### Flutter 对齐

Figma 设计语言要能映射到 Flutter 实现。

- Figma 组件尽量对应 Flutter Widget 或 Widget 组合。
- 颜色、间距、圆角、字号和断点要能进入 Flutter theme 或常量文件。
- 组合组件要说明哪些属性允许覆盖，避免研发重新猜。
- 如果一个 Figma 效果在 Flutter 中实现成本很高，要在评审时提前标注。

## 组件复用

组件复用从三件事开始：

- 创建 component。
- 编辑 component。
- 覆盖 instance。

组件组织要服务于研发实现。单个按钮、输入框、标签、卡片可以作为基础组件；搜索区、筛选区、列表项、表单区可以作为组合组件。组合组件要尽量对应 Flutter 里的 Widget 组合，方便研发按页面结构拆实现。

当前不固化统一组件分组名。正式项目只要求先把基础组件、组合组件和业务组件区分清楚；如果后续形成量潮统一 Figma 组件库，再把真实组件分组补进本手册。

组件不能只看起来一样，还要说明可变属性。例如尺寸、状态、图标、文字、禁用、加载、危险操作，都要在组件或旁注里表达清楚。

## 模板和教学

新手不知道从哪里开始时，可以先用模板练手。

- 官方模板用于学习基础操作。
- 社区模板用于快速理解常见页面结构。
- 量潮课堂原型可以公开一个要素完整的早期版本，作为训练用参考答案。
- 模板临摹结束后，要回到量潮自己的组件、命名和交付标准。

模板不能直接变成交付物。复制来的页面要经过业务流程、组件命名、响应式和研发可实现性检查。

## 响应式设计

响应式设计不能等前端开发时再临场处理。不同尺寸的交互思路可能互相冲突，需要提前妥协；固定尺寸容易，比例和自适应会更麻烦。

量潮 Figma 文件至少说明：

- 基准尺寸是什么。
- 小屏、中屏、大屏分别怎么布局。
- 哪些区域固定，哪些区域自适应。
- 列表、表格、表单和导航在不同尺寸下怎么变化。
- Figma 的约束关系如何对应 Flutter 的布局约束。

断点目前只确认“小、中、大”的基本分法：

| 断点 | 对应设备 |
|------|----------|
| 小 | 手机 |
| 中 | 平板 |
| 大 | 电脑 |

现有资料没有确认量潮统一像素值，所以本手册不凭空写具体宽度。如果项目采用 Material Design、Microsoft 或其他断点标准，要在项目文件里标注参考来源和实际取值，不能只写“响应式”三个字。

## 插件

插件优先围绕 Material Design 和 Flutter 选型。

安装插件时：

1. 在 Figma 插件搜索框搜索目标关键词，例如 `Material Design` 或 `Flutter`。
2. 从搜索结果中选择需要的插件。
3. 在文件或项目说明里记录插件名称和用途。
4. 插件生成的组件要进入量潮自己的组件检查，不能直接原样混入正式组件库。

插件适合提高效率，但不能代替设计语言。凡是会影响交付的颜色、组件、图标、网格和断点，都要最终沉淀为量潮项目自己的约定。正式插件清单要等实际使用和验证后再写入，不凭空推荐。

## 团队协作

Figma 协作要让评论、决议和实现任务能追得回来。

- 评审前，把评审入口 Page、主流程 Frame 和待确认问题整理好。
- 评论时尽量点到具体 Frame 或组件，不在群里留下无法定位的口头意见。
- 产品负责确认流程和文案。
- 设计负责确认视觉、组件和状态。
- 研发负责确认实现成本、响应式和 Flutter 对应关系。
- 评审结束后，把结论同步到项目任务或 GitHub Issue，不只留在 Figma 评论里。

多人协作时，草稿区、评审区、确认区和归档区要分开。不要让未确认方案和已确认方案混在同一个页面里。

## 版本历史

量潮使用 Angular Git commit message 风格管理 Figma 版本历史。版本名要说明变更类型、范围和动作。

格式示例：

```text
feat(login): add phone-code prototype
fix(layout): adjust mobile breakpoint
docs(component): annotate form validation states
refactor(home): split dashboard frames
```

这些示例只说明命名格式，不代表真实项目版本记录。

版本历史至少在这些节点记录：

- 第一次完整低保真流程。
- 第一次可点击原型。
- 高保真视觉评审前。
- 研发实现前的冻结版。
- 重大交互或断点调整后。
- 线上验收后的归档版。

不要用“改了一版”“最新版”“最终版2”这种版本名。Figma 文件可以很自由，但量潮项目需要能追踪设计决策。

## 交付标准

Figma 文件交付前要满足：

- Project、File、Page、Frame 层级清楚。
- 主流程能通过 Present 跑通。
- 关键状态齐全：空、错、加载、成功、失败、禁用。
- 颜色、网格、断点和组件规则能被研发复用。
- Material Design 和 Flutter 的对应关系已经说明。
- 组件、instance 和 override 的使用关系清楚。
- 插件来源和用途清楚。
- 评审评论已经处理或转成任务。
- 版本历史使用 Angular Git commit message 风格记录。

## 发布前检查

- 是否确认本文件属于语言、框架和工具目录
- 是否已经从外链切换为本地页
- 是否保留 Project、File、Page、Frame 的层级说明
- 是否写清 Material Design、网格、颜色和 Flutter 对齐
- 是否写清组件、模板、插件、响应式和版本历史
- 是否避免空泛的 Figma 功能介绍
- 是否没有把未确认的断点值、固定页面模板、组件分组名和插件清单写成量潮规范
- 是否保留量潮项目评审、任务留痕和研发协作要求
