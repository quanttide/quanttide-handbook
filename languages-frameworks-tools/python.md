# Python手册

量潮工作手册语言、框架和工具目录下的 Python 子手册，讲的是怎么把一段 Python 从“能在自己电脑上跑”整理成可复现、可测试、可交付、可维护的工程资产。Python 可以写脚本，也可以写服务和数据任务，但都要先把环境、依赖、入口和测试说清楚。

## Python 使用场景

- 一次性脚本、命令行工具、后台服务、数据处理任务和批处理流程。
- 需要虚拟环境、依赖锁定、测试和发布记录的 Python 项目。
- 需要被 CI、定时任务、云函数或其他系统稳定调用的执行入口。
- 需要 AI 辅助起草、解释错误、重构模块或补充测试的代码工作。

## 工程约束

- 先固定 Python 版本和环境管理方式，再写代码。
- 依赖必须可复现，不能只停留在本机临时安装状态。
- 入口、参数、配置和错误输出要稳定，方便别人调用和排查。
- 测试覆盖关键路径和边界，再进入发布或自动化调度。
- 代码、配置、文档和运行示例要一起维护。
- 生成式辅助可以用，但必须人工确认逻辑、依赖和异常处理。

## 代码维护角色

- 负责人确认这个 Python 项目解决什么问题、交付到哪里。
- 开发负责模块拆分、入口设计、错误处理和代码维护。
- 测试负责验证核心功能、边界条件、回归和性能风险。
- 平台负责运行环境、依赖安装、CI、定时任务和发布流程。
- AI 负责辅助起草代码、解释报错、整理结构和补测试建议。

## 工程对象

| 对象 | 含义 |
|------|------|
| `project` | Python 项目本体 |
| `environment` | 运行环境 |
| `dependency` | 依赖包和版本 |
| `script` | 一次性执行脚本 |
| `package` | 可复用包 |
| `test` | 测试用例 |
| `artifact` | 构建或发布产物 |
| `release` | 发布记录 |

## 从环境到发布

### 运行环境

先把 Python 环境准备好。任何脚本进入长期维护前，都要知道它依赖哪个 Python 版本和哪些包。

- 确认 Python 版本
- 确认虚拟环境工具
- 确认依赖安装方式
- 确认系统路径和权限

### 项目结构

把项目结构整理清楚。脚本可以简单，但不能把入口、配置、业务逻辑和测试全部混在一起。

- 明确入口文件
- 明确包结构
- 明确配置文件
- 明确测试目录

### 模块开发

开发阶段只做可追踪的改动。函数边界、异常处理和日志输出要服务于后续排查。

- 保持函数和模块职责清楚
- 避免过度耦合
- 保留必要注释
- 记录关键变更

### 测试回归

测试阶段确认代码不是只“能跑”。至少覆盖正常输入、空输入、错误输入和外部依赖失败。

- 写单元测试
- 写必要的集成测试
- 覆盖边界条件
- 检查回归风险

### 打包发布

发布阶段把稳定版本交出去。发布对象可以是脚本、包、镜像、CLI 或定时任务，但都要能回到版本记录。

- 固定版本号
- 锁定依赖
- 生成发布产物
- 保留发布证据

### 依赖维护

维护阶段处理后续变化。Python 项目的主要风险通常来自依赖升级、运行环境变化和隐式输入格式变化。

- 修复 bug
- 升级依赖
- 记录兼容性变化
- 保持文档同步

## 典型任务

- 自动化脚本：重点看参数、日志、幂等性和失败重试。
- 命令行工具：重点看帮助信息、退出码、配置文件和版本号。
- Web 服务：重点看接口契约、依赖注入、错误响应和部署方式。
- 数据采集和处理：重点看输入来源、字段口径、质量检查和输出格式。
- 文档转换和批处理：重点看文件编码、路径规则、异常文件和处理报告。
- AI 辅助工作流：重点看提示词、输入脱敏、输出校验和人工确认。

## 代码交付标准

- 有明确的运行入口、参数说明和示例命令。
- 有可复现的环境说明和依赖锁定方式。
- 有测试和回归记录，至少覆盖关键路径。
- 有日志、错误输出或处理报告，便于定位失败。
- 有发布说明、变更记录和必要的回退方式。

## 提交前检查

- Python 版本是否明确
- 依赖是否锁定
- 入口是否清楚
- 测试是否通过
- 配置是否齐全
- 发布是否可回退
- 文档是否同步
