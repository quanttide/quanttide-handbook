# 项目管理手册

量潮工作手册管理目录下的项目管理子手册，用以指导量潮及其合作伙伴的项目管理事务。当前版本重点处理项目、事项、会议议题、项目范围管理和客户交付流程，尤其是如何把一个有明确交付目标的事项，变成边界清楚、责任清楚、验收清楚、资料可复盘的项目。

项目管理关注生产和交付。按照团队管理手册里的边界判断，只有在有明确客户、明确交付目标、明确验收边界和明确交付时间时，才把一件事命名为“项目”。其他内部研发、文档沉淀和资产积累，不强行放进项目管理里。

## 项目管理边界

项目管理优先处理这些对象：

- 项目：围绕明确目标、范围、交付物、时间和资源组织的一次性工作。
- 项目集：相互关联、需要统一协调的一组项目。
- 项目组合：为了战略目标、资源配置和优先级管理放在一起管理的一组项目或项目集。
- 事项：敏捷管理中的里程碑、史诗、用户故事、任务等工作对象。
- 会议：围绕议题、议程、发言、记录、草案和决议推进项目判断。
- 范围书：定义项目应该做什么、不做什么、交付什么、如何验收。

不适合直接命名为项目的情况：

- 只有想法，没有客户、使用方或验收方。
- 只有内部学习和探索，没有交付边界。
- 只是长期资产建设，例如文档、代码仓库、数据处理器和知识库沉淀。
- 只是团队协作动作，例如目标对齐、分工、沟通、评审、交接和复盘。

这些事项可以先进入产品研发、团队协作或数字资产管理，再在出现明确交付目标后转成项目。

## 项目和事项

项目管理先把两组对象分开：项目、项目集、项目组合属于项目层级；里程碑、史诗、用户故事、任务属于事项层级。

| 对象 | 使用场景 | 管理重点 |
|------|----------|----------|
| 项目 | 有明确目标、范围、交付物和期限 | 范围、进度、资源、风险、验收 |
| 项目集 | 多个项目共同服务一个阶段目标 | 项目间依赖、资源冲突、统一节奏 |
| 项目组合 | 多个项目或项目集共同服务组织战略 | 优先级、投入产出、战略一致性 |
| 里程碑 | 标记关键节点或阶段完成 | 时间点、条件、验收信号 |
| 史诗 | 较大的需求或工作包 | 拆分边界、业务价值、阶段计划 |
| 用户故事 | 从用户或客户视角描述的需求 | 角色、目标、价值、验收条件 |
| 任务 | 可以分配和执行的具体动作 | 负责人、截止时间、完成标准 |

事项不能只写标题。至少要写清：

- 为什么做。
- 属于哪个项目、项目集或项目组合。
- 当前对象是里程碑、史诗、用户故事还是任务。
- 谁发起，谁负责，谁验收。
- 预期交付物是什么。
- 完成以后进入哪里归档或复盘。

## 会议议题

项目会议需要使用“议题格式”，用来规范会前提交待讨论问题的方式。

议题包括：

- 序号：正整数，标记议题提交顺序；会前通常整理成讨论顺序。
- 标题：动词短语，说明具体需要做什么事情。
- 描述：长文本，描述具体内容，并附上必要的草案等链接。
- 发起者：姓名，问题的最初提出者，通常也是第一个发言。
- 发言者：姓名，需要就这个议题发言的人。
- 记录者：姓名，负责落实议题的人或者部门。
- 草案：文档，对某个问题的决议初稿，提交到会议上讨论。
- 决议：文档，经过辩论、修改、投票以后的草案。

议题示例：

```text
议题1：评审议题格式草案

议题格式用以规范会前提交待讨论问题的格式。详见：https://example.com

发起者：张三

发言者：

- 张三@CEO办公室：介绍从政治学中吸收的议题、议程、议事原则的概念。
- 李四@项目管理部：汇报项目管理部制定的议题格式草案。
- 王五@人力资源部：补充人力资源部关于议题格式草案的初步评审意见。

记录者：

- 赵六@项目管理部：负责在后续会议中落实议题格式。
```

项目会议不能只留下聊天记录。会前要有议题，会中要有讨论和修改，会后要有决议、负责人和后续任务。需要工程或文档执行的内容，应进入 GitHub Issue、PR、计划或对应工作手册。

## 项目范围管理

项目范围管理包括确保项目包含且仅包含完成项目所需全部工作的过程。它要定义和控制项目应该包括什么、不应该包括什么。

范围管理包括这些子过程：

- 收集需求（Collect Requirements）。
- 定义范围（Define Scope）。
- 创建工作分解结构（Create Work Breakdown Structure，WBS）。
- 核实范围（Verify Scope）。
- 控制范围（Control Scope）。

范围管理要先回答：

- 客户或验收方是谁。
- 项目目标是什么。
- 项目范围内包括哪些工作。
- 明确不包括哪些工作。
- 交付物有哪些。
- 每个交付物的质量标准是什么。
- 哪些需求会影响成本、时间或资源。
- 范围变更由谁批准。

## 范围书验收

项目范围书评审主要看完整性、准确性、一致性和可行性。

### 完整性

目标完整性：项目范围书应明确阐述项目总体目标。目标应该具体、可衡量、可达成、相关、有时限，符合 SMART 原则。

例如，一个软件开发项目可以写成：“在接下来的 12 个月内，开发一个能够支持 10 万用户并发访问，且系统崩溃率低于 1% 的电商 APP。”如果只写“开发一个电商 APP”，目标就过于模糊。

工作内容完整性：范围书要列出从项目启动到交付的各阶段工作，包括设计、开发、测试、部署等。建筑项目不仅要包含主体建筑施工，还应涵盖附属设施建设、场地清理、绿化等工作。

交付成果完整性：范围书要规定所有交付成果。产品研发项目的交付成果可能包括产品原型、测试报告、用户手册等，并说明具体规格和质量标准，例如产品原型达到什么功能完整度、测试报告包含哪些测试用例覆盖范围。

### 准确性

范围边界准确性：范围书要清楚说明哪些工作属于项目范围，哪些不属于。比如企业资源规划（ERP）系统升级项目，要说明只升级财务和库存管理模块，人力资源模块不在本次升级范围内。

需求描述准确性：功能性需求要说明系统或产品能做什么，例如电商 APP 中用户能够完成商品浏览、下单、支付。非功能性需求要说明性能、可靠性、安全性等要求，例如响应时间在 3 秒内，安全防护等级达到行业标准。

### 一致性

与项目战略一致性：范围书内容要服务组织战略。如果组织战略是拓展线上业务，那么线上营销平台建设项目的功能模块、系统性能和交付成果都应围绕线上营销能力展开。

内部一致性：范围书内部各部分不能互相冲突。交付成果质量标准要和工作任务相匹配，项目进度安排要和资源分配、工作范围相协调，不能用过少资源在过短时间内完成过多工作。

### 可行性

技术可行性：范围书规定的工作内容和交付成果要在现有技术条件下可实现。比如虚拟现实（VR）游戏项目，不能要求在不支持高级图形渲染的硬件平台上实现超逼真的 3D 场景。

资源可行性：范围书要考虑人力、物力、财力是否能满足。如果项目范围要求短时间内完成大量工作，而现有人力无法承担，或者特殊设备、材料无法及时获取，就需要重新评估范围。

时间可行性：范围书规定的进度和交付时间要合理。软件开发项目中的测试工作必须在开发工作基本完成后才能开始，不能把测试阶段安排在开发工作刚开始的时候。各阶段时间估算要符合行业标准和项目实际情况，不能过于乐观。

## 量潮项目交付流程

量潮真实项目记录里，项目交付不是“把文件发出去”这么简单，而是从资料接手、范围确认、交付物生成、客户验收、正式交付到复盘沉淀的一条链路。

基本流程：

1. 接手项目：确认客户、项目目标、交付范围、当前进度、历史资料、代码仓库、数据来源和交接人。
2. 集中资料：客户项目资料进入 GitHub 私有仓库，大文件进入 Dropbox、阿里云对象存储或其他约定渠道，客户聊天记录进入项目资料目录。
3. 定义交付物：列清原始资料、结构化数据、说明文档、审计清单、代码、运行脚本和最终报告。
4. 先做核验样例：对风险高、数据量大或客户判断不确定的项目，先交 example 或一个年份/批次给客户核验。
5. 等待客户验收反馈：样例或首批交付通过后，再继续交付后续批次。
6. 正式交付：通过官方通知渠道发送说明和链接，通过大文件渠道传输数据，通过客户群或企业微信群补充通知。
7. 更新进度：把客户是否收到、是否反馈、是否验收、后续批次是否可交付写回项目进度。
8. 复盘沉淀：整理时间线、卡点、返工原因、客户反馈和后续平台研发需求。

数据交付项目常见交付物：

| 交付物 | 内容 |
|--------|------|
| 原始文件包 | 原始 HTML、TXT、图片、压缩包或其他原始资料副本 |
| 结构化数据集 | CSV、JSONL、数据库表或最终面板数据集 |
| 交付说明 | 统计结果、字段说明、验收标准、交叉验证方法 |
| 分类审计清单 | manifest.csv/jsonl，每条记录对应分类、来源和证据 |
| 代码交付集 | 完整项目代码、脚本、运行入口和依赖说明 |
| 代码逻辑说明书 | 处理流程、关键函数、输入输出、复现方式 |

一个已经跑通过的交付顺序可以这样写：

```text
2014 example 交付客户核验 -> 客户反馈通过 -> 2015/2016 交付物上传 -> Gmail 通知客户 -> Dropbox 或对象存储传输大文件 -> 企业微信群补充通知 -> 记录客户验收状态
```

这个顺序的重点是：不要把“上传完成”误认为“客户验收完成”。上传只是交付动作，客户收到、能打开、能核验、反馈通过，才进入下一批交付或项目收尾。

## 项目任务记录模板

项目任务要能让后来接手的人知道背景、目标、做法和完成标准。只写一句“处理某项目”不够。

推荐格式：

```text
- [ ] 任务标题 YYYY/MM/DD

  背景：为什么有这个任务，来自客户反馈、会议决议、邮件安排还是项目卡点。
  目标：这次任务要解决什么问题。
  步骤：
  1. 第一步动作。
  2. 第二步动作。
  3. 第三步动作。
  完成标准：做到什么程度算完成，由谁确认。
  进展：按日期记录关键进展、阻塞和判断变化。
  结果：完成、作废、延期、等待反馈或转入其他任务。
```

任务记录里要保留这些具体信息：

- 客户或使用方是谁。
- 当前卡点是什么。
- 谁是负责人、执行人、验收人。
- 使用哪个仓库、目录、工具或交付渠道。
- 完成标准是否能被第三方检查。
- 如果任务作废，作废原因和替代方案是什么。

例如，数据项目重跑任务不能只写“重跑数据”。至少要写清：客户催进度，首批交付物需要 example 供客户核验；交接资料缺失时，按复现制度重跑；数据来自公开来源，Dropbox 只是交付渠道；完成标准是首批结果核验通过、后续批次交付闭环。

## 客户验收和交付渠道

客户交付要把通知渠道、文件渠道和验收状态分开。

| 类型 | 作用 | 常见载体 |
|------|------|----------|
| 官方通知 | 告诉客户交付内容、链接、验收方式和后续动作 | Gmail |
| 大文件传输 | 放置数据包、代码包、压缩包和最终文件 | Dropbox、阿里云 OSS |
| 补充通知 | 提醒客户查看、补充说明、同步进度 | 企业微信群、客户群 |
| 项目记录 | 保存交付物清单、时间线、验收状态和负责人 | GitHub 私有仓库、项目进度文档 |

交付前检查：

- 交付物是否和范围书一致。
- 文件是否完整，压缩包是否可解压。
- 结构化数据是否有字段说明。
- 代码是否有运行说明。
- 大文件链接是否可访问。
- 客户是否知道先验收哪一批。
- 后续批次是否依赖首批验收结果。

交付后检查：

- 客户是否收到通知。
- 客户是否能打开链接。
- 客户是否开始核验。
- 客户反馈是否已记录。
- 客户通过后，后续年份、批次或版本是否可以继续交付。
- 如果客户未回复，谁负责跟进，何时跟进。

## 项目复盘流程

项目复盘分为内部复盘和外部复盘。

内部复盘主要梳理整个项目的工作历史和交付过程。项目亲历者优先参与；如果有人离职，就由交接人负责补齐历史资料。复盘时要查询邮件、客户群、GitHub 仓库、对象存储、网盘、会议记录和任务记录，把项目时间线梳理清楚。

内部复盘重点看：

- 哪个环节卡住了。
- 哪个环节返工了。
- 哪个环节依赖个人记忆。
- 哪个交接信息没有传下来。
- 哪个资料没有进入仓库或对象存储。
- 哪个交付动作被误认为验收完成。
- 哪些摩擦可以转成平台研发需求。

外部复盘主要把和客户相关度高的部分整理成复盘报告发给客户。报告里要说明我们完成了什么、哪里做得不够、后续希望客户如何配合，以及类似项目下次怎么减少重复错误。

复盘报告有两个作用：

- 帮助后续项目减少重复错误，提高交付效率。
- 为平台研发提供上下文。业务中的摩擦，就是量潮项目云、量潮数据云、量潮商务云等系统后续要解决的问题。

量潮项目管理中有一个重要链条：

```text
数字化 -> 复盘 -> 平台研发
```

整理和数字化是基础，复盘发现摩擦，平台研发再把这些摩擦变成产品功能、数据结构、流程页面或命令行工具。

## MVP 项目模板

MVP 项目要先验证最小闭环，不要一开始就做完整系统。

一个可用的 MVP 项目文档至少包括：

- 负责人：负责产品判断和推进。
- 验收人：代表真实使用方确认是否可用。
- 事实源使用方：后续系统或流程依赖谁的确认结果。
- 项目背景：当前问题是什么，为什么现在要做。
- 项目目标：要建立什么闭环。
- MVP 范围：本期实现什么，本期不实现什么。
- 角色职责：用 RACI 或类似方式说明谁负责、谁批准、谁协作、谁知会。
- MVP 流程：从触发到结果如何流转。
- 审批或状态设计：最小状态集是什么。
- Decision Log：关键产品决策、理由和边界。
- 验收标准：功能验收和业务验收分开写。
- 后续阶段：MVP 通过后继续做什么。

例如，一个账本配套审批 MVP 的闭环可以写成：

```text
实训执行 -> 账本记录 -> 配套审批 -> 审批结果确认 -> 业务系统可信记录 -> 对账一致
```

这个例子的核心原则是：审批结果作为事实源，账本记录与业务系统记录都以审批结果作为可信依据。

MVP 阶段可以明确“不做什么”。例如第一阶段只做审批单创建、关联账本记录、审批验收、审批结果记录和审批历史追溯；不做多级审批、会签审批、自动流转、消息通知和复杂权限管理。这样能避免项目范围在第一版就失控。

## 婚礼项目示例

婚庆管理可以作为项目管理示例。婚庆管理本质是以情感交付为导向的轻量级项目。它涉及审美、人际关系等软性因素，但目标管理、风险控制和资源协调仍然能显著提升筹备效率与成功率。

这个示例的价值在于：它提醒项目管理不能只用于软件、工程和商业交付，也可以用于一次性、不可逆、利益相关方复杂的事件。

### 契合

明确目标与范围：

- 婚礼目标是在规定时间、预算内完成一场符合新人期待的仪式。
- 范围管理要界定“婚礼包含什么”，例如场地、婚纱、摄影。
- 范围管理也要界定“不包含什么”，例如是否涵盖蜜月行程。

时间节点驱动：

- 可以用甘特图式进度表拆分任务，例如选场地、试妆、发请柬。
- 关键动作要对齐时间节点，例如提前 3 个月预订酒店。
- 里程碑事件包括领证、试菜、婚礼彩排等。

资源与成本控制：

- 预算分配要平衡刚性支出和弹性支出，例如场地费是刚性支出，装饰布置是弹性支出。
- 要预留应急资金。
- 要协调婚庆公司、摄影团队、餐饮等外部资源，这类似项目管理中的外包管理。

风险管理：

- 雨天备用场地。
- 设备故障应急方案。
- 宾客突发缺席应对措施。
- 双方父母对流程期待不同造成的冲突协调。

### 特殊性

强情感属性：

- 需求优先级要先说清，例如“仪式感大于规模”或“亲友体验大于视觉效果”。
- 筹备压力可能引发新人焦虑，需要通过沟通和进度透明化缓解。

多角色协同复杂性：

- 利益相关方包括新人、双方家庭、伴郎伴娘、宾客等。
- 可以用 RACI 矩阵明确责任分工，例如谁负责确认菜单，谁通知亲友。
- 要避免信息不对称，例如婚庆公司改了流程但没有同步给摄影团队。

临时性与唯一性：

- 婚礼是一次性项目，试错成本极高，流程错误无法重来。
- 交付要根据新人偏好定制，类似敏捷项目管理中的迭代调整。

### 方法

工具适配：

- 用 Trello 或 Excel 跟踪任务进度。
- 用 Notion 整合合同、预算表、宾客名单。
- 用关键路径法（CPM）识别最长任务链，例如“订酒店 -> 发请柬 -> 确认人数”。

方法论适配：

- 用 WBS 拆解任务，例如一级任务“场地筹备”，二级任务“签合同、布置、设备调试”。
- 用 PDCA 循环持续优化细节，例如彩排后调整流程顺序。

## 项目管理检查

- 这件事是否真的应该命名为项目？
- 是否有明确客户、使用方或验收方？
- 是否区分了项目、项目集、项目组合？
- 是否区分了里程碑、史诗、用户故事和任务？
- 会前是否提交了议题？
- 议题是否包含序号、标题、描述、发起者、发言者、记录者、草案和决议？
- 项目范围是否说明包含什么、不包含什么？
- 是否完成收集需求、定义范围、创建 WBS、核实范围和控制范围？
- 范围书是否满足完整性、准确性、一致性和可行性？
- 目标是否符合 SMART 原则？
- 交付成果是否有规格和质量标准？
- 范围边界是否防止范围蔓延？
- 需求是否同时覆盖功能性需求和非功能性需求？
- 技术、资源和时间是否可行？
- 项目资料是否已经进入 GitHub 私有仓库、对象存储或约定资料库？
- 交付物是否区分原始资料、结构化数据、交付说明、审计清单、代码和逻辑说明？
- 是否把上传完成、通知完成和客户验收完成分开记录？
- 是否有内部复盘、外部复盘和摩擦点清单？
- MVP 项目是否明确负责人、验收人、事实源使用方、范围和 Decision Log？
- 一次性、不可逆、强情感或多角色协同项目是否单独做风险预案？
