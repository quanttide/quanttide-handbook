# 数字资产管理手册

量潮工作手册管理目录下的数字资产管理子手册，讲的是怎么把文档、会议材料、代码仓库、数据处理器、共享文件和外部平台资料变成可分类、可命名、可授权、可迁移、可审计的组织资产。数字资产管理不是把文件堆进一个空间，而是让每一类资产知道归谁管、放哪里、叫什么、谁能看、什么时候归档。

## 资产管理边界

数字资产包括组织在日常协作、研发、交付和经营中持续产生、需要复用或留痕的数字化资源。

重点管理对象：

- 文档：草稿、方案、议题、计划、标准、手册、教程和归档资料。
- 会议材料：会议纪要、录屏、转写文本、演示材料和决议记录。
- 代码资产：Git 仓库、脚手架、工具库、应用、配置和发布记录。
- 数据资产：数据处理器、数据字典、数据集、处理报告和质量记录。
- 产品材料：BRD、PRD、交互稿、用户文档、测试材料和验收记录。
- 共享空间文件：微盘、OSS、知识库、在线文档和其他协作平台中的文件。

不纳入本手册直接管理的对象：

- 财务付款、发票和合同原件，优先进入财务管理链路。
- 人事档案和个人隐私材料，优先进入人力资源和权限管理链路。
- 未确认可公开或可共享的客户材料，先按保密规则处理。

## 资产分类

资产分类要服务于查找、权限和迁移，不只是为了整理文件夹。

建议按四层描述：

| 层级 | 含义 | 示例 |
|------|------|------|
| 领域 | 资产属于哪个业务或管理领域 | 团队协作、数据工程、产品研发 |
| 子领域 | 领域下的具体事项 | 议事管理、数据处理器、文档维护 |
| 资产类型 | 资产是什么形态 | 议题、计划、手册、代码仓库、会议录屏 |
| 实例 | 具体文件、仓库或记录 | 某次会议录屏、某个 Python 仓库 |

文件夹或资产名称可以采用：

```text
<领域>-<子领域>-<资产类型>
```

例如：

```text
团队协作-议事管理-议题
文档工程-文档管理-草稿
数据工程-处理器管理-数据处理器
```

具体命名例子要优先保留：

```text
2024年第6周-常委会议题4-微盘资源治理
qtcloud-data-provider
qtcloud-data-architecture-docs
quanttide-tutorial-of-
```

其中：

- 议题文档可以按`<年份和周数>-<委员会和编号>-<简化的标题>`命名。
- 代码平台类资产可采用`品牌标识-功能标识（-语言和框架标识）`。
- 文档平台类资产可采用`品牌标识-功能标识-docs`。
- 教程类资产可采用`quanttide-tutorial-of-`前缀。

## 责任和权限

每类数字资产都要有明确的维护责任，不能只靠“谁上传谁负责”。

- 资产负责人确认分类、命名、权限和归档口径。
- 维护人负责更新内容、修正命名、处理重复文件和同步状态。
- 使用人负责按约定位置读取、引用和反馈问题。
- 审核人负责确认资产是否可以发布、归档、删除或迁移。
- 平台负责人负责共享空间、OSS、GitHub、知识库等平台权限。

权限设置要遵循：

- 默认最小权限，按工作需要开放。
- 外部共享必须有负责人确认。
- 可公开材料、内部材料、敏感材料分开存放。
- 重要资产的删除、迁移和公开发布要留下记录。

## 命名规则

命名规则要让别人不打开文件也能判断它大概是什么。

通用命名建议：

- 名称包含领域、事项、资产类型和必要时间。
- 避免使用“最终版”“最新版”“临时”“新建文件”。
- 同一类资产使用同一套日期、版本和编号规则。
- 可以用语义化版本表示重要材料版本。
- 文件名和标题尽量一致，避免下载后丢失上下文。

常见命名口径：

| 类型 | 命名关注点 |
|------|------------|
| 议题文档 | 年份周数、委员会或会议、编号、简短标题 |
| 工作计划 | 时间周期、项目或部门、计划类型 |
| 会议录屏 | 会议日期、会议主题、材料类型 |
| 代码仓库 | 品牌标识、功能标识、语言或框架标识 |
| 文档仓库 | 品牌标识、主题标识、`docs` 或手册类型 |

## 文档流转

文档类资产要区分草稿、已解决、悬而未决和已归档。

### 草稿

草稿先在个人或部门空间产生，再汇总到统一空间。

推荐路径：

```text
个人 -> 部门空间 -> 公司数字资产空间 -> 对应文档仓库或归档目录
```

微盘路径可以更具体：

```text
个人 -> 部门（如微盘“CEO办公室”） -> 公司（微盘“数字资产”空间） -> 文档工程-文档管理-草稿
```

草稿阶段要说明：

- 谁发起
- 要解决什么问题
- 当前版本是否可引用
- 下一步由谁处理

### 已解决文档

已经通过流程审议或确认的文档，应进入对应仓库、知识库或正式归档目录。

- 正式规范进入对应 GitHub 文档仓库。
- 已经审议完毕的草稿，通过 PR 提交到对应 GitHub 仓库。
- 可复用材料进入知识库或数字资产空间。
- 对外发布材料进入发布流程。
- 提交后清理重复草稿，避免多个版本同时流转。

### 悬而未决文档

讨论后还没有定论的内容，不直接当作正式规则。

- 提交到对应 GitHub 仓库中的 Issue、任务或决策记录。
- 标记问题、争议点、负责人和下一次处理时间。
- 讨论清楚后走 PR 流程提交到仓库，再进入正式文档或归档。

## 会议材料

会议材料是高频数字资产，重点是纪要、录屏、转写文本和决议记录要能互相对应。

### 会议纪要

会议纪要至少包括：

- 会议时间
- 会议主题
- 参会人
- 讨论事项
- 决策结论
- 待办事项
- 负责人和截止时间

### 会议录屏

录屏要根据平台空间和稳定性选择云端录制或本地录制。

- 空间充足时优先使用云端录制。
- 空间不足且来不及清理时使用本地录制。
- 视频文件和转写文本要成对归档。

录屏归档流程：

1. 用企业微信账号登录腾讯会议管理后台的录屏管理页面。
2. 点进每个录屏，分别另存为“视频内容”和“转写文本 - 原文版 - txt文本”。
3. 按`会议日期_会议内容.mp4`和`会议日期_会议内容.txt`命名。
4. 上传到指定数字资产空间；腾讯会议录屏当前归档到阿里云 OSS 存储桶`quanttide-collab`的`meeting-records`目录。
5. 将录屏、转写文本、会议纪要和相关待办链接互相对应。
6. 确认备份文件可访问、命名正确、权限正确后，再清理腾讯会议网页中的源录屏。

删除源录屏前必须确认：

- 视频文件已经完整上传。
- 转写文本已经同步归档。
- 会议纪要已经记录录屏或资产位置。
- 权限范围符合会议材料的公开级别。
- 负责人确认不再依赖会议平台原始文件。

归档时建议保留：

- 视频文件
- 转写文本
- 会议纪要
- 相关演示材料
- 决议或待办链接

## 数据处理器资产

数据处理器是连接文档、测试和代码的工程资产。

一个数据处理器至少要能对应：

- 文档：说明模块功能、设计思路、输入输出和验收标准。
- 测试：列出关键测试场景、边界条件和回归用例。
- 代码：实现处理逻辑、入口、模型和依赖。
- 运行记录：记录参数、输入、输出、耗时和错误。

建议目录关系：

| 资产 | 说明 |
|------|------|
| `docs/` | 处理器说明、验收标准和测试设计 |
| `src/` | 处理器代码、仓储、模型和入口 |
| `tests/` | 单元测试 |
| `integrated_tests/` | 集成测试 |
| `reports/` | 运行结果、质量检查和交付记录 |

数据处理器模块示例包括：

- `src/repositories`模块。
- `tests/test_main`模块。
- `integrated_tests/test_main`模块。

数据处理器进入数字资产管理时，要同时检查文档、测试和代码是否一致。

## 代码和仓库资产

代码仓库也是数字资产。仓库命名、说明、文档和归档状态要统一管理。

代码类仓库命名通常关注：

- 品牌标识
- 功能标识
- 语言或框架标识
- 客户端、服务端、SDK、CLI、控制台等形态

文档类仓库命名通常关注：

- 品牌标识
- 主题标识
- 手册、教程、标准、架构文档等文档类型

仓库资产至少要有：

- 清晰的 README
- 当前维护状态
- 入口文档或目录
- 发布或归档说明
- 负责人或维护团队

## 迁移和清理

数字资产长期堆积后，最容易出现重复、过期、无主和权限混乱。

需要定期清理：

- 已经进入正式仓库的草稿。
- 多个版本并存但没有主版本的文档。
- 已下载、已备份但仍占用平台空间的录屏。
- 不再维护但没有归档说明的仓库。
- 权限过宽或外链过期的共享文件。

迁移时要记录：

- 从哪里迁出
- 迁到哪里
- 迁移人
- 迁移时间
- 是否保留旧链接
- 是否需要通知使用人

## 资产检查

- 资产分类是否清楚
- 负责人和维护人是否明确
- 命名是否能看出领域、类型和时间
- 权限是否符合最小可用原则
- 草稿、正式版和归档版是否分开
- 会议录屏、纪要、转写文本和 OSS 备份是否能对应
- 数据处理器的文档、测试和代码是否一致
- 微盘“CEO办公室”“数字资产”空间和 GitHub 仓库之间的流转是否清楚
- 议题、代码仓库、文档仓库和教程的命名例子是否保留
- 已迁移资产是否清理重复副本
- 删除、公开发布或迁移是否留下记录
