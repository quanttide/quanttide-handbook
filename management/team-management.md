# 团队管理手册

量潮工作手册管理目录下的团队管理子手册，讲的是管理者如何在目标不完全清楚、流程还没有标准化、员工认知不一致的时候做判断、分配、沟通和纠偏。团队管理不是替代产品研发、团队协作、项目管理、数字资产管理等专项手册，而是处理这些专项手册还没有覆盖的管理问题。

本手册的定位是：管理者如何管理员工，或者上级管理者如何管理下级管理者。它以政治学和管理学为基础，给企业管理和公共管理建立统一的理论框架，用来指导还没有形成标准化管理体系的问题。

这个定位背后还有一层现实背景：企业与公共机构的边界正在变得模糊，企业管理和公共管理之间有越来越多可以互相借鉴的经验。本手册不把管理问题只看成公司内部行政问题，而是把团队治理、公共决策、组织适应能力和员工发展一起放进管理者的判断框架里。

## 管理边界

团队管理优先处理这些对象：

- 人和人的权责关系。
- 管理者和员工之间的授权、反馈和信任。
- 目标、计划、资源、风险和优先级。
- 还没有沉淀到专项手册里的新问题。
- 横跨多个管理手册、需要负责人做综合判断的问题。

已经有明确专项手册的事项，优先进入对应手册：

| 事项 | 优先进入 |
|------|----------|
| 需求、规划、设计、研发、验收、上线和复盘 | 产品研发手册 |
| 目标对齐、分工、沟通、评审、交接和复盘 | 团队协作手册 |
| 有明确客户交付目标的事项 | 项目管理手册 |
| 文档、会议材料、代码仓库、数据处理器和共享空间 | 数字资产管理手册 |
| 现金流、采购、付款、凭证和财务规则 | 财务管理手册 |
| 赛事筛选、参赛立项、材料生产和路演答辩 | 创赛管理手册 |

团队管理手册要负责的是这些专项规则背后的判断方式：什么时候授权，什么时候收口，什么时候公开讨论，什么时候进入制度化。

## 管理原则

### 权力平等

管理者和员工在职位权力上不同，但在人格和价值上平等。管理者的权力不是天然凌驾于团队之上，而是来自团队合作契约中的授权和信任。

从社会契约的视角看，职位权力差异不否定本质平等。管理者的权力来源于员工让渡出来的一部分协作权力，本质上是一种授托权力。它的合法性来自契约的双向性，也就是说，管理者不仅拥有协调和决策权，也必须承担服务团队、解释决策、接受约束的责任。

权力来源要分成两类看：

- 员工固有权利：每位员工都拥有参与工作的权利、劳动保障权利和职业发展权利，这是权力平等的基础。
- 管理者授托权力：管理者的权力来自员工基于合作契约让渡的部分权力，用来促进团队目标达成和资源优化配置。

这个原则对应三个判断：

- 合法性：管理者行使权力要能说明它服务于团队共同目标。
- 服务性：管理者要提供资源、支持、指导和协调，而不是只下命令。
- 限制性：员工没有让渡的基本权利不能被职位权力覆盖。

落到工作中，管理者要做到：

- 重大事项说明决策依据和目标。
- 把可以交给员工判断的事项授权出去。
- 给被授权的人配套资源、信息和反馈。
- 定期检查权力是否过度集中在少数人身上。
- 对权力使用后的结果负责。

### 激励相容

团队管理不能只要求员工服从目标，也要让他们的成长、成就感和责任边界与团队目标对得上。管理者承担更大的压力和风险，必须面对公司的各种挑战，并为团队的成功或失败负责；员工更多关注自身发展、成就感和个人价值提升。两边的激励如果不相容，管理动作就会变成短期压任务。

员工如果能感受到自己在公司中如同“主人公”般存在，就更有可能承担更多责任和义务。这里的“主人公”不是口号，而是让个人成长、公司目标和管理者激励形成正向反馈。

管理者要优先设计这些机制：

- 让员工知道自己的工作如何影响团队目标。
- 给员工足够自主权，让他们能对结果产生主人翁意识。
- 把参与决策、承担责任和获得成长机会连在一起。
- 对贡献、风险和责任做匹配反馈。
- 避免只把压力向下传递，却不把信息、资源和收益向下同步。

### 实证

团队管理里的实证原则，是要求管理判断回到事实、案例、记录和结果，不能只靠身份、经验和口头感觉。

管理者做判断时，优先看这些证据：

- 任务记录：任务是否有目标、负责人、截止时间、阻塞和结果。
- 会议记录：讨论过什么，形成了什么结论，谁负责落实。
- 交付物：文档、代码、设计稿、数据、报告或其他可检查成果。
- 协作记录：GitHub Issue、PR、评审意见、计划、议题和复盘记录。
- 客户或使用方反馈：需求是否真实，结果是否被使用，问题是否复现。
- 财务和资源记录：预算、采购、付款、工具订阅和人力投入是否支持原判断。

管理判断按这个顺序形成：

1. 先记录事实，不先给员工贴标签。
2. 再提出解释，说明可能原因。
3. 找到能验证解释的材料。
4. 用小范围动作试行修正。
5. 复盘结果，决定是否形成规则。

例如，不能只说“员工不主动”，要先看目标是否清楚、权限是否给足、任务是否过大、反馈是否及时、成果是否被承认。也不能只说“沟通不顺”，要看会议结论有没有记录、议题有没有负责人、后续任务有没有进入计划或 GitHub Issue。

如果实际结果和原判断冲突，要修正规则，而不是只要求员工适应旧规则。

### 信息透明

信息透明不是所有信息无差别公开，而是让参与工作的人能拿到完成判断和行动所必需的信息。

团队管理中要透明的内容包括：

- 目标：为什么做这件事，服务哪个团队目标。
- 依据：为什么这样判断，有哪些事实、约束和前提。
- 边界：哪些事情在范围内，哪些事情不在范围内。
- 分工：谁负责决策，谁负责执行，谁负责记录，谁负责验收。
- 资源：可用预算、时间、人力、工具和外部支持。
- 风险：已经出现或可能出现的阻塞、冲突和例外。
- 结果：决议、任务、交付物、复盘结论和规则变更。

透明的基本载体：

- 会议结论进入会议纪要。
- 待讨论问题进入议题。
- 要执行的动作进入计划或任务。
- 工程和文档事项进入 GitHub Issue 或 PR。
- 已确认的规则进入对应工作手册。

不适合完全公开的信息也要有边界说明。涉及员工隐私、薪酬、客户保密、合同细节、账号权限、安全风险和未公开商业信息时，不公开具体内容，但要说明由谁负责、为什么受限、后续如何确认。

## 管理职能

团队管理不是每件事都亲自做，而是让决策、计划、组织、领导、控制和创新这些职能在团队里有人负责、有人协作、有人检查。

| 职能 | 管理者要回答的问题 |
|------|--------------------|
| 决策 | 哪些事必须现在判断，哪些事可以继续观察 |
| 计划 | 事情有哪些环节，关键节点在哪里 |
| 组织 | 谁做什么，资源怎么配，责任怎么落 |
| 领导 | 如何让员工理解目标并愿意投入 |
| 控制 | 哪些指标、节点和风险需要持续检查 |
| 创新 | 旧方法不适用时，如何试出新的工作方式 |

### 计划

计划不是把任务排满，而是先把事情拆开。

计划阶段要问：

- 事情有哪些环节？
- 每个环节交给谁做最有比较优势？
- 哪些环节是关键的，出错会打乱全局？
- 哪些环节允许更多尝试，用来积累经验？
- 关键节点怎么控制？
- 哪些问题一出现就需要及时跟踪？

管理者和普通执行者的差异在于视角。执行者可以专注当前任务，管理者要把视角拉高到全局，判断一个局部不顺利会不会影响整体结果，从而分清主次。

### 沟通

现代组织里的管理者需要处理不同背景、不同利益关系、不同信息位置的人。沟通不是把话说完，而是协调利益、解决冲突，并培养团队的沟通意识和能力。

沟通时至少确认：

- 员工是否知道目标。
- 员工是否知道自己的责任边界。
- 员工是否知道可以使用哪些资源。
- 员工是否知道问题出现后找谁。
- 多方之间是否对结论有同一理解。
- 决策、分歧和待办是否留下记录。

管理者要避免两种沟通失效：

- 只同步结论，不同步原因，导致员工无法自主判断。
- 只收集问题，不明确下一步，导致沟通变成情绪堆积。

## 治理分工

团队管理要和其他管理手册分清边界，避免所有事情都被叫成“项目”，也避免研发成果散落在过程记录里。

### 项目管理

项目管理关注生产和交付。有明确客户交付目标的时候，定义为一个“项目”；其他事情不命名为“项目”，尤其是内部研发体系。

因此，团队管理中遇到事项时先判断：

- 是否有明确客户？
- 是否有明确交付目标？
- 是否有明确验收边界？
- 是否有明确交付时间？

如果答案成立，进入项目管理手册；如果不成立，可能属于产品研发、团队协作或数字资产管理。

### 数字资产管理

数字资产管理关注研发和积累。

团队管理中保留几个具体判断：

- 微盘是草稿箱，GitHub 仓库放正式资源。
- “计划”“议题”“文档草稿”的管理，分别由团队协作手册和文档管理手册集中移到数字资产管理手册里。
- 内部研发体系从项目管理体系中拿出来，不再关注研发过程，而是关注研发目标和研发结果。
- 研发结果要被定义为数字资产的积累。

团队管理者在分配任务时，要区分“交付给客户的项目”和“沉淀给组织的资产”。前者看交付目标，后者看积累价值。

## 文化管理

### 使命和愿景

使命回答“组织现在为什么存在、正在做什么”，愿景回答“组织未来想成为什么”。使命偏当前，愿景偏未来；使命用于日常判断，愿景用于长期方向。

管理者在带团队时，要把使命和愿景落到具体工作里：

- 当前任务服务什么组织使命。
- 当前积累会把组织推向什么未来状态。
- 员工在这个过程中能形成什么能力。
- 任务完成后会留下什么可复用资产。

### 价值观

价值观本质上是一种有限理性策略。它不是口号，而是在信息不完整、时间不充足、成本不能无限增加时，团队用来快速做一致判断的策略。

管理者维护价值观时，要持续回答：

- 哪些判断应该被团队反复使用？
- 哪些行为应该被鼓励？
- 哪些行为即使短期有效，也不应该被默许？
- 新员工如何从真实案例中理解价值观？
- 价值观是否已经进入招聘、培养、协作、评审和复盘？

## 管理制度

管理制度要解决两类问题：重要事项如何公开议事并形成决议；没有成文规则时，历史案例如何沉淀成可复用规则。

### 议会民主制

议会民主制不是把所有管理动作都拿来投票，而是把影响范围大、需要共同承诺、容易产生争议的事项放到公开议事流程里。

适合公开议事的事项：

- 修改团队规则、手册和长期工作方式。
- 调整跨团队职责、权限和资源分配。
- 确认影响多人的预算、工具、流程和协作机制。
- 处理员工普遍关心但没有现成规则的问题。
- 对旧规则做例外处理，且这个例外可能成为新规则。

不适合公开议事的事项：

- 已经有明确负责人和明确规则的日常执行事项。
- 紧急安全、客户事故、线上故障等需要先止损的事项。
- 涉及员工隐私、薪酬、合同保密和账号安全的敏感细节。

公开议事按这个流程走：

1. 提交议题：写清标题、背景、要解决的问题、草案和期望结果。
2. 安排议程：确认讨论顺序、发言人、记录人和决议方式。
3. 陈述事实：先说明证据和约束，再表达观点。
4. 辩论修订：围绕草案改文本，不只停留在态度表达。
5. 形成决议：通过表决或明确共识确认结论。
6. 指定落实：明确负责人、执行动作、完成时间和验收方式。
7. 记录归档：把决议放到会议纪要、计划、Issue、PR 或对应手册。

决议记录至少包括：

- 议题标题
- 背景和事实
- 主要分歧
- 最终决议
- 适用范围
- 生效时间
- 负责人和记录人
- 后续检查时间

### 判例法制度

判例法制度用于处理还没有成文规则、但已经发生过类似情况的问题。它的重点不是照搬旧案例，而是把旧案例里的事实、理由、边界和结果沉淀下来，供下一次判断参考。

适合沉淀判例的情况：

- 某类问题反复出现，但还没形成固定制度。
- 一次例外处理暴露了旧规则的缺口。
- 管理者做过重要裁量，需要说明理由。
- 员工对同类问题的处理公平性有疑问。
- 新员工需要通过真实案例理解价值观和管理规则。

一个管理判例至少记录：

| 字段 | 内容 |
|------|------|
| 事实 | 当时发生了什么，有哪些证据 |
| 问题 | 争议点或待判断事项是什么 |
| 处理 | 最终怎么处理，由谁决定 |
| 理由 | 为什么这样处理，排除了哪些方案 |
| 边界 | 这个案例适用于哪些情况，不适用于哪些情况 |
| 后续 | 是否需要进入手册、流程、权限或考核规则 |

引用旧案例时，要先比较事实是否相似：

- 工作目标是否相同。
- 责任边界是否相同。
- 资源约束是否相同。
- 影响范围是否相同。
- 员工是否处在相同信息条件下。

如果事实差异很大，旧案例只能作为参考，不能直接覆盖新问题。多个案例重复指向同一个判断时，应把它们整理成正式规则，进入对应工作手册。

## 团队管理检查

- 当前问题是否已经有专项手册承接？
- 如果没有专项规则，是否需要团队管理者先做判断？
- 权力使用是否说明了目标、依据和影响范围？
- 授权是否配套资源、信息和反馈？
- 员工激励是否和团队目标相容？
- 计划是否拆清环节、负责人和关键节点？
- 沟通是否留下结论、分歧和待办？
- 事项是否被错误命名为“项目”？
- 研发成果是否进入数字资产积累？
- 使命、愿景和价值观是否能指导当前判断？
- 信息透明是否覆盖目标、依据、边界、分工、资源、风险和结果？
- 实证判断是否回到任务、会议、交付物、Issue、PR、反馈和资源记录？
- 需要公开议事的事项是否形成议题、决议和落实记录？
- 没有成文规则的新问题是否沉淀成可复用判例？
