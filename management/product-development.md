# 产品研发手册

量潮工作手册管理目录下的产品研发子手册，记录从需求发现、产品策划、原型设计、领域建模、工程实现、测试发布到复盘的工作方法。产品研发要在亲身体验中寻找需求，并把需求、设计、API、代码、文档和版本发布串成一个可协作的流程。

## 产品工作范围

产品研发的交付物大体分为三类：

- 面向用户的交付物：前端、后端、API 文档、用户文档。
- 面向社区的开源文档：基础教程、工作手册、工程标准。
- 面向研发团队的设计资料：README、架构设计、接口设计、测试说明等。

典型工作包括：

- 市场调研：调研市场需求和已有竞品，形成用户调研文档和竞品分析文档。
- 产品设计：规划产品形态，形成产品策划文档和产品原型图。
- 领域建模：抽象系统概念，形成工程标准、架构设计文档和 API 文档预览版。
- 工程实现：形成前后端代码、API 文档正式版和用户文档，并交付给用户。

## 产品判断原则

- 先在真实体验中寻找需求，再写功能列表。
- 先定义问题、用户和场景，再定义功能。
- 先做低保真和 Demo，把方向跑通后再做高保真。
- 需求变更必须能说清为什么改、改了什么、谁确认。
- 设计、研发和验收共用同一套目标、约束和证据链。
- 产品判断必须有人负责，AI 只能辅助草拟、拆解和比较方案。

## 产品协作角色

- 负责人确认目标、范围、优先级和上线口径。
- 产品经理完成 PRD、用户故事、版本计划和需求评审。
- 项目经理组织 Scrum Plan 会议，形成 Coding 项目协同的迭代计划。
- 设计负责低保真、高保真、Figma 原型和交互说明。
- 前端负责 UI 实现、Mock API 接入和客户端发布。
- 后端负责 API 设计、实现、部署和接口文档。
- QA 按 Coding 测试管理中的测试计划验收。
- AI 负责整理信息、生成草稿、提示遗漏和辅助比较方案。

## PRD 和用户故事

产品需求文档是指导产品开发的主要文档，由应用的产品经理负责完成，并在产品团队及管理层代表的需求评审会上确定。

PRD 和用户故事约定：

- 应用的产品团队协作 Coding 项目中的`<name>-prd`作为产品需求文档。
- 产品策划在 PRD 文档中以用户故事形式阐述需求。
- 必要时带上低保真原型图和初步版本迭代计划。
- 产品需求文档可以包含用户画像、产品特性、产品原型等。
- 产品特性主要基于用户故事地图梳理，单篇文档遵循用户故事格式。
- 非正式材料可以通过问答或交谈整理成用户故事文档，必要时替代传统 PRD。

事项层级可以按项目类型区分：

- 软件研发类项目采用用户故事地图，分为“用户活动”“用户任务”“史诗”“用户故事”四级。
- 手册教程类项目采用标准 Scrum，分为“史诗”和“需求/任务”两级。

## 从问题到上线

### 发现问题

先确认问题本身是否值得做。

- 收集用户、客户、内部团队和市场输入。
- 判断问题边界。
- 明确受众。
- 记录约束条件。
- 形成用户调研或竞品分析文档。

### 澄清需求

澄清阶段把模糊想法变成可讨论的需求。

- 统一术语。
- 确认目标。
- 排除歧义。
- 定义验收方式。
- 写入`<name>-prd`或对应需求文档。

### 规划版本

项目经理在 Scrum Plan 会议前协助产品策划补全版本迭代计划，并在会议后维护定稿。

- 确认本轮做什么、不做什么。
- 拆成史诗、用户故事或任务。
- 定义依赖和负责人。
- 形成 Coding 项目协同的迭代计划。

### 设计原型

设计原型阶段主要使用 Figma 等原型设计软件。实际经验是：

1. 产品先画一轮低保真。
2. 前端拉一个 Demo。
3. 设计做几轮高保真。
4. 前端再改几轮。
5. 初期可以先用纸笔画，通过后再上 Figma 画初稿。
6. 到 Flutter 阶段，可以直接开 Debug 现场调整。

这个流程承认“一轮设计不到位”的现实，通过低保真、Demo、高保真、Debug 多轮迭代降低返工风险。

### API 和架构设计

量潮更偏 Design-First API：在后端实现之前先约定 API，方便测试驱动开发和前后端协作。

API 文档责任可以由架构师或产品经理承担：

- 情况复杂时由架构师主导。
- 简单 RESTful API 可以由产品经理负责。
- 后端实现后导出 API 文档正式版。

产品研发中的架构设计可使用：

- 领域驱动设计（DDD）。
- 事件风暴。
- 领域模型。
- 产品全景图。
- 用户故事地图。

工程原则上遵循云原生标准，包括容器化、无状态、不可变、基于 API 的协作等。

## 工程实现

迭代流程：

1. 产品策划在 PRD 中写用户故事，必要时附低保真和版本计划。
2. 项目经理发起 Scrum Plan 会议评估需求、制定计划。
3. 交互设计师根据 PRD 和 Scrum Plan 制作高保真原型。
4. 前端工程师根据原型实现客户端 UI；有 Mock API 时可先接 Mock。
5. 架构师、后端工程师或产品经理先设计 API 并发布 API 文档，和前端确认。
6. 后端工程师按 API 文档实现服务，并部署到预生产环境。
7. 前后端联调，前端接入后端服务端 API。
8. QA 按 Coding 测试管理的测试计划检查是否符合预期。
9. 验收通过后部署到生产环境。

客户端和服务端可以分开发布版本；一个产品版本的完成主要以客户端发布和上线为准。

## 技术选型

选型口径包括：

- 客户端框架：Flutter，覆盖 Mobile/PC Web、Android、iOS、Windows、Mac。
- Web 端基础：Vite + React/Vue + TailwindCSS + Flowbite。
- React 方向可使用 Flowbite-React。
- 设计语言：自建系统和客户应用以 Material Design 作为设计语言原型，原因是完备性和生态较好，也是 Flutter 的默认标准。
- 设计转代码工具可关注 PixelFree Studio，从 Figma 导入设计并生成代码。

选型要记录原因，不只记录结果。

## SDK 需求和 APIClient

SDK 开发规范适合放在产品研发的“需求到 SDK”场景。

APIClient 类用于实现与云产品基于网络协议的通信。常见设计：

- `BaseAPIClient`负责传参、初始化、密钥传递和身份认证。
- 身份认证字段按 API 机制命名，例如`access_token`。
- 通用请求入口可以命名为`request_api`。
- 各 API 模块用 Mixin 拆分，再组合成用户使用的`APIClient`。

API 分层：

| 层级 | 含义 |
|------|------|
| low-level API | 实现通信协议、鉴权算法、请求和返回值解析验证 |
| high-level API | 对应 API 文档做稳定封装 |
| integrated API | 根据用户需求封装 high-level API，通常快速迭代 |

模块划分要尽量遵循官方 API 文档，例如 Coding OpenAPI 可以按项目、仓库、CI 等模块划分。单元测试模块也可以对应 API 模块划分。

Python 等动态语言缺少原生 mixin 静态识别能力时，新开发者可以通过全局搜索寻找 API 实现位置：

- macOS：`Command+Shift+F`
- Windows：`Ctrl+Shift+F`

Python SDK 对外 API 优先遵循 Python 语言习惯，使用蛇形命名；不要为了跨语言一致性把 Python 写成 Java 风格。

## 版本发布

产品研发约定版本发布层级：

- alpha 版本：通常发布在开发环境，版本号为`x.x.x-alpha.x`。
- beta 版本：通常发布在测试环境，版本号为`x.x.x-beta.x`。
- pre-release 和 release：通常发布在生产环境，版本号为`x.x.x-rc.x`或`x.x.x`。

发布前要确认：

- PRD、API 文档、测试计划和代码实现是否一致。
- 客户端和服务端是否需要分开发布。
- 预生产环境是否已验证。
- 用户文档和 API 文档是否同步。
- 回退方式是否明确。

## 上线后反馈

用户经常在团队控制范围以外的场景和设备环境下使用产品，因此要重点收集各种情况并提出解决方案。

反馈至少记录：

- 用户场景。
- 设备和环境。
- 产品特性或缺陷。
- 复现路径。
- 处理方案。
- 是否进入下一轮迭代。

## 上线前检查

- PRD 是否进入`<name>-prd`或对应文档位置
- 用户故事、用户画像、产品特性和原型是否对应
- 低保真、Demo、高保真和实现是否对齐
- API 文档是否先于后端实现完成必要约定
- 前后端联调是否完成
- Coding 测试计划是否验收通过
- alpha、beta、rc 或 release 版本定位是否清楚
- 客户端、服务端、API 文档和用户文档是否同步
- 上线是否可观察、可回退、可复盘
